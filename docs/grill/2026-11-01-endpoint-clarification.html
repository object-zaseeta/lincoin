決まったこと

基準 C は「公開最速級実装を主、無い課題は AI 最適化 C」とする

再現可能で第三者が検証できることを最優先にした。
The Computer Language Benchmarks Game などの公開上位実装を正とし、公開実装がない課題はフロンティア AI に時間制限なしで最適化させた C を使う。
AI 生成の基準 C は生成過程をリポジトリに残す。
人間の専門家への依頼は、コストと再現性の問題で捨てた。

成功率 95% は複数社のフロンティア級モデルの全てで満たす

「特定モデル専用の言語」という疑いを避けるため、単一モデル固定を捨てた。
評価ラウンドごとに対象モデルを選び、モデルID・設定・プロンプトをリポジトリに記録する。
合格判定は全モデルで 95% 以上(過半数・平均は主張が弱まるため捨てた)。

トークン効率「Python 以下」を完成条件に追加する

一文ゴールの「少ないトークンで」に対応する合格ラインが完成条件になかった。
「同じ課題を同じモデルに Python で解かせた場合の総トークン(読む+書く+やり直し)以下」を条件2に足した。
検証付きの言語が検証なしの Python より安い、という強い主張になる。

旧条件3(実用稼働)と旧条件4(自分で使う)を統合する

「実用で動いている」の定義がなかったため、具体的だった条件4に稼働基準を足して1本にした。
新条件: zaseeta.com の公開機能のロジックの一部を、仕様と例の承認だけ(手書きテストなし)で出荷し、30日以上、出荷ロジックのバグ修正なしで稼働。

v1.0 の射程を「CLI ツール・データ処理・計算カーネル」と明記する

「汎用言語」の看板と狭い完成条件のずれを、射程の明記で解消した。
設計は汎用を壊さないまま、完成判定は測れる範囲に閉じる。
汎用化(GUI 接続・サーバー常駐の本格対応)は完成後の方向とし、完成条件に含めない。

まだ決まっていないこと

  • 評価ラウンドの対象モデルの具体名 — 各ラウンド開始時に決めて記録する
  • GitHub リポジトリの名前と公開範囲 — ユーザーがリモート作成時に決める(push はユーザーが行う)

範囲

  • やらないこと: 数値の確定(フェーズ2)、ベンチマーク基盤の実装、GitHub への push

用語

エンドポイント: このプロジェクトを完成と判定するための条件集合。vision.md §4 に置く。
基準 C: 完成条件1で速度比較の正とする C 実装。公開最速級実装、無ければ AI 最適化 C。
性能契約: 「割り当てなし」「境界チェックが残らない」など、満たせなければコンパイルエラーになる性能の約束。
フロンティア級モデル: 評価時点で各社の最上位にある生成 AI モデル。

検討の記録

  1. 「専門家の C」を何で調達するか — 推奨: 公開最速実装+AI 最適化 C → 決定: 推奨どおり。再現性と公開時の説得力を優先
  2. 成功率 95% を測る AI の固定方法 — 推奨: 評価時点の最新モデル1つを記録付きで固定 → 決定: 複数モデルで測る(推奨と異なる)。特定モデル依存の疑いを消す方を取った
  3. 複数モデル時の合格判定 — 推奨: 全モデルで 95% → 決定: 推奨どおり
  4. トークン効率の合格ライン — 推奨: Python 以下を完成条件に追加 → 決定: 推奨どおり
  5. 「実用で動いている」の定義 — 推奨: 条件4と統合し30日稼働基準 → 決定: 推奨どおり
  6. 「汎用言語」の看板と狭い完成条件のずれ — 推奨: v1.0 の射程を明記 → 決定: 推奨どおり
  7. Lincoin の独立リポジトリ化 — 推奨: 今この場で git init → 決定: 推奨どおり。ただしサンドボックスが .git 作成を拒否したため、git init -b main はユーザーが実行する
